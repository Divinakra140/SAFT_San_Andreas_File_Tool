===================================================================================================
CHANGELOG 1.0 - Making SAFT run under Android PC emulation (Winlator)
===================================================================================================

SAFT now runs successfully under Android PC emulation (Winlator), in addition to native Windows.
This section lists what actually made that happen.

Confirmed working emulators (as of August 2026) : Tested on Retroid Pocket Flip 2 SD865
-------------------------------------------------
- Winlator 11.1 Official by bruno dev
- Winlator Bionic Vanilla 3.1 by StevenMXZ

Confirmed NOT working (the SAFT app won't even open):
- Winlator Star
- GameHub Lite

Successful Container Settings Used:

Best Box64 preset: Stability

Startup Selection: Any, even Aggressive works.

Wine Version: Winlator Official 11.1 I used default wine settings.

For Winlator Bionic I  used Proton-9.0-x86_64-0 this is box, not fex.

DXVK Version: 2.3.1 worked in Bionic and 2.4.1 worked in Official (default for both)

GPU driver was default for both, newest mxz turnip 26.2.0 R7-Oneui was also used and worked.

Screen size can be reduced to 940 x 544 to see text more clearly, works at larger resolutions.

Changes
----------------

1. Rewrote the entire GUI from WPF (what the original pre-Winlator build used), to WinForms.
   WPF renders through DirectX/DirectWrite, which Wine emulates poorly. WinForms renders through
   GDI/GDI+, a much older and far more thoroughly Wine-tested API. This was the single biggest
   change - without it, the app didn't render at all under Winlator, even though it ran fine on
   real Windows.

2. Fixed the clouds background not showing up.
   The clouds image and the window's main content layer were structured as siblings instead of
   parent/child. WinForms' "transparent" background only sees through to its actual parent, not
   whatever's behind it in the same layer, so the content layer's transparency was falling through
   to a plain gray instead of the clouds behind it.

3. Fixed the log/output list being crushed or missing entirely on some tabs.
   Label heights were being measured before the window had ever actually been laid out, which
   wildly overestimated how much space wrapped description text needed. That inflated size ate
   into - or on some tabs, completely swallowed - the space meant for the log list underneath it.

4. Fixed the Yes/No confirmation windows showing cut-off text and buttons.
   Same root cause as #3, in the separate confirmation dialog window: its size was locked in
   before its real, wrapped-text height was known, cutting off both the warning message and the
   buttons below it.

5. Replaced File.Copy + File.Delete with File.Move when finishing a rebuilt archive.
   When a mod is too big to patch in place, SAFT rebuilds the whole archive into a temp file, then
   has to put that file where the original was. The old approach read and wrote the entire archive
   a second time to do that - slow anywhere, and extra load on Wine's file APIs specifically. A
   move is a near-instant rename instead of a second full copy.

6. Throttled progress reporting during archive rebuilds.
   The rebuild was reporting progress on every single file - upwards of 16,000 times for a full
   archive - each one a message posted across to the app's UI thread. Under Winlator this could
   build up faster than the UI thread could keep up with, eventually crashing partway through an
   otherwise-successful rebuild. Reporting every 25th file instead (still looks smooth) resolved a
   crash that had been happening reliably partway through large rebuilds.

7. Made the final "put the rebuilt archive in place" step crash-safe.
   The most serious issue: swapping the freshly rebuilt archive in for the original, if
   interrupted partway through, could destroy the original before the replacement was safely in
   place. Rewritten so the original is renamed aside first (not deleted), the replacement is moved
   in, and only then is the set-aside original cleaned up. If the move fails for any reason, the
   original is automatically restored. Also self-healing: if something ever still manages to leave
   a set-aside original behind, the next run detects and restores it automatically before doing
   anything else.

8. Made a single corrupted audio mod file unable to derail an entire install.
   A malformed .wav (a bad "data chunk size" field, in one real case) could throw an obscure
   OverflowException that aborted the whole install - including archives already successfully
   rebuilt and other audio files already patched. Now the bad file's size is validated up front
   (with a clear error naming the actual file instead of a cryptic crash), and if a file still
   fails for any other reason during the actual patch, it's skipped and reported by name rather
   than taking everything else down with it.

9. Fixed overlapping text on the "Install Mod(s) into Extracted" and "Rebuild from Extracted" tabs.
   The manifest summary (shown after picking an extracted folder) starts out blank and only gets
   its real, longer, two-line text once a folder is actually picked - so the space reserved for it
   at startup (based on the blank string) never grew to fit, and the real text overlapped whatever
   was placed right below it. Fixed the same way as item 3: reserve space for a realistic worst
   case up front instead of the blank string. Applied the same fix preemptively to the Extract
   tab's scan-results text, which had the identical risk but hadn't been reported yet.

Result
------
All five tabs are confirmed fully functional under Winlator: extraction, installing into an
extracted copy, rebuilding, direct install/rebuild, and uninstalling mods from a vanilla backup.
Mods that are too big to patch in place (needing a full archive rebuild) install successfully and
work correctly in-game, confirmed with three separate real-world car mods (a Nissan Skyline, a
Nissan 300ZX, and a Toyota Supra swap) and a full modpack (an enhanced weapons pack) replacing
models, textures, every SFX package, and every streamed radio station - all patched successfully
with no failures.


Current time estimates on tasks within an emulated windows container on android: based on testing every function.
------------------------------------------------------------------------------
 Tab 1. Extracting an entire game directory without audio: 1.5 hours
 Tab 2. Installing mods into extracted directory: 30 seconds or so depending on mod size.
 Tab 3. Rebuilding game from extracted folder: 10-20 minutes or so
 Tab 4. Installing mods into game folder without extraction: 30 seconds or so depending on mod size.
 Tab 5. Uninstalling mods from a vanilla backup: same as tab 4 - it is the same engine run in
        reverse, so it takes as long as installing the same set of files did.

CHANGELOG 1.6 - Six new file types, and a rule about game scripts
===================================================================================================

Changes from version 1.0 to 1.6: added 6 new file types that SAFT can replace, totaling in 11.

Changes
-------

10. Added replacement of game files that live outside the archives (map mods, finally).
   San Andreas keeps map geometry in the .img archives but map PLACEMENT in loose text files -
   data/maps/*.ipl and *.ide - plus path nodes, data tables and loose textures. SAFT only ever
   matched archive entries and audio, so all of that came back as "unmatched" and had to be copied
   in by hand, which meant a map mod could never be a single SAFT-installable package. Those files
   are now matched by name and replaced exactly like archive entries, backed up the same way, on
   every install/uninstall path. Executables, .dll/.asi libraries and whole .img archives are
   deliberately never eligible - SAFT replaces game assets, not the game itself.

   One real subtlety this turned up: 66 filenames exist BOTH inside an archive and loose in the
   game folder. 64 of them (the nodes0.dat-nodes63.dat path tables) are byte-for-byte identical in
   both places, where replacing only one copy risks the game loading the stale other one - so both
   are updated together. The other two (arrow.dff, hoop.dff) are genuinely different files that
   merely share a name, where no tool can know which one a mod meant. Rather than guess, SAFT
   compares the game's own two copies: identical means update both, different means replace the
   archived copy and report the other instead of silently overwriting it.

11. SAFT will no longer replace game scripts (.scm) at all, and says why.
   This one is a rule, not a limitation: SAFT only installs what it can genuinely uninstall.
   Every other file SAFT touches is a leaf asset - restore the original and the change is fully
   undone. Scripts aren't. San Andreas save files are written against the script's global variable
   layout (defined by data/script/main.scm), and they also store a table of streamed-script records
   that reference the scripts inside script.img BY INDEX - confirmed by reading a real save
   directly: 25 records, 20 bytes each, named DANCER, PCHAIR, OTBWTCH, PEDROUL and so on, matching
   script.img's own entries one for one. Replace either kind and an existing save can hold live
   references into bytecode that no longer matches it. Saves live in the user's Documents folder,
   outside the game directory, so no backup SAFT makes can undo that damage.

   So both are refused now - the loose main.scm AND the streamed scripts inside script.img, even
   though the latter are ordinary archive entries SAFT is perfectly capable of patching. When a mod
   folder contains either, SAFT says so in plain language rather than silently ignoring the file,
   and the two get different instructions because installing them by hand is a different job:
   main.scm is one loose file at data > script > main.scm that can simply be dragged over, whereas
   a streamed script only comes out of script.img by extracting the game, dropping the .scm into the
   extracted script.img folder, and rebuilding - all of which SAFT's own first and third tabs do.
   Everything else in the mod still installs normally either way.

Result
------
SAFT now replaces 11 categories of game file, up from 5:

  1. Models          .dff
  2. Collision       .col
  3. Textures        .txd
  4. Animations      .ifp
  5. Audio           .wav for SFX, .ogg for music
  6. Map Data        .ipl placement, .ide object definitions
  7. Paths           nodes .dat, .rrr car recordings
  8. Data Tables     .dat, .cfg, .zon, .ped, .grp
  9. Text            .gxt
 10. Cutscenes       .cut, .mpg
 11. Particle Effects .fxp

That is essentially every asset in the game. For scale, a stock v3 install holds 15,334 models,
3,983 textures, 435 animations, 426 car recordings, 251 collision files, 190 map placement files
and 212 data tables inside the archives, plus another 398 files sitting loose in the game folder.
SAFT can replace all of them.

Deliberately never replaced: .exe (the game itself), .dll and .asi (libraries and plugins -
modloader/CLEO territory), .img (whole archives, which SAFT works inside of rather than swapping),
and .scm (game scripts, per item 11 above, SAFT will never run the chance of corrupting any saves.)


===================================================================================================
CHANGELOG 2.0 - Adding content, two editions, and knowing when a mod is too heavy
===================================================================================================

Up to 1.6 SAFT could replace things. It can now ADD things, it ships in two editions, and it can
tell you before you install whether a mod is heavy enough to break your game's rendering.


Two editions
------------
SAFT.exe - Install Mods and Uninstall Mods. Two tabs. Everything in it finishes in seconds, which
is what makes it honest to recommend for Winlator.

SAFT-Dev.exe - the same two tabs plus Extract Game Files, Install Mod(s) into Extracted and Rebuild
from Extracted. Those three are the only route to some things, but they write over 20,000 individual
files, which takes about half an hour on a desktop and far longer on Android. Windows recommended.

One source tree builds both, so a fix in one is a fix in the other.


Adding new content
------------------
A mod folder can now contain assets the game has never seen, not just replacements for assets it
already has. SAFT works out which is which from the file names: anything matching a game file is a
replacement, anything that does not is an addition.

For an addition SAFT finds free object slots (a stock game has about 5,127 of them), writes the
object definitions and placements into its own .ide and .ipl, registers those with the game, and
merges any collision records into the shared bundle. Uninstall reverses all of it.

Object collision is mandatory and SAFT enforces it: placing an object with no collision record
crashes San Andreas on world load, every time, wherever the object happens to be. An EMPTY collision
record is legal and gives a walk-through object, so SAFT allows that and says so.

If your files are not named the same as the game files they were meant to replace, SAFT now stops
and asks before treating them as additions - a taxi replacement has to be called taxi.dff, and
without that question you could follow every later prompt correctly and still not get your taxi.


Knowing when a mod is too heavy
-------------------------------
SAFT measures how much your game will have to load in one place after a mod is installed, and
compares it against what a stock copy loads there. The bands come from playing the game at each
weight rather than from a formula:

  GREEN   up to 2.2x vanilla   renders perfectly everywhere
  AMBER   2.3x to 3.1x         rendering breaks where the mod loads heaviest, rest of the game fine
  RED     above 3.2x           rendering breaks everywhere; around 4x it can also crash

The figure is absolute, not relative, so installing onto an already-heavy game is judged on the game
you end up with rather than on the size of the step.


Backups
-------
Backups are no longer optional. They hold only the entries that actually get replaced - a mod
touching a dozen files costs a few megabytes - and they are the only thing the Uninstall tab can
restore from, so turning them off was really turning off uninstalling.

FIXED, and the reason this changed: in 1.6, backing up while a mod was already installed could
overwrite a vanilla backup with the modded file, destroying the only clean copy. Backups are now
never overwritten once written.


Speed and reliability
---------------------
- Installing and uninstalling no longer copy the game to a temporary folder first. On a handheld
  that took over 40 minutes and wrote 900 MB to internal storage; the same job now takes seconds.
- Replacements smaller than the file they replace now shrink the entry properly, so a lighter mod
  actually lightens what the game loads instead of streaming the old size.
- SAFT writes saft-activity-log.txt next to the exe, one line per step, flushed as it goes, so a
  problem can be located instead of guessed at.
